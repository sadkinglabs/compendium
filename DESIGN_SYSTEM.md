# DESIGN_SYSTEM.md — Compendium visual language

The single governed source of truth for Compendium's visual language, tokens, primitives, patterns, and platform-render rules. Grounded in what the five pillars (**Home · Codex · Collection · Decks · Play**) ship today, reconciled through a read-only audit + independent review (`docs/design-system/`). Every agent must consult this file before UI work; a reviewer may reject an invented colour or primitive by citing it.

> **Status is load-bearing.** Every entry is tagged. **Implementation may use only `[Shipping]`/Observed vocabulary.** `[Target]` = owner-approved but **not implemented** (adoption is a separate later track); `[Candidate]` = unproven; `[Exception]` = sanctioned shipping wall; `[Deprecated]` = retire. Do not reference a `[Target]`/`[Candidate]` token or component as if it exists.
>
> **Status legend:** `[Shipping]` available now (the only usable vocabulary) · `[Exception]` ships today, sanctioned · `[Target]` owner-approved, not implemented · `[Candidate]` provisional · `[Deprecated]` retire.
> **Promotion** `[Candidate] → [Proposed Target] → (owner OD ruling) → [Target] → (adoption) → [Shipping]`.
> Source of record: `src/theme/tokens.css` (values) · `docs/design-system/design-system-wave1-synthesis.md` (evidence + OD ledger, owner-ruled 2026-07-19).

## 2 · Semantic layer

- **Single accent per pillar** (the "one accent dot" rule): Home/Codex gold · Decks violet · Play jade · Collection ruby. Chrome is black + gold; the pillar accent is a functional dot, not a wash of the UI.
- **Two documented `[Exception]` walls** (owner-ruled OD-12 — *current-state exceptions, not permanent ideals; migration requires its own device-verified proposal*):
  1. **Decks `.cx-decks`** — a scoped amethyst world (`--bg #0b0714`, amethyst borders/bg-grad) plus the **deliberate violet two-tone** (chrome `--accent-violet #c79ad0` vs content `#a08cc0`/`#c9a8e8`). Documented in `decks.css` ("replicate, do not redesign").
  2. **Play `.cx-life-tracker`** (`counter.css`) — a scoped vocabulary. **Three genuine same-name overrides** collide with `:root` and mean different things inside this scope: `--bg` (`#0e0b08`), `--gold` (= `--gold-leaf`), `--gold-head` (`#e3c589`). The rest (`--text/--muted/--body/--surface/--border`) are a **parallel vocabulary** with no `:root` twin. Document these as scope-local so no reader assumes `--gold` is global.
- **Status colours** (`--win`/`--loss`/`--destructive`) are a **distinct semantic axis** from wayfinding accents and must not be conflated (OD-7).

## 4 · Patterns
*Each pattern is `[Shipping]` (it exists in the app today) unless tagged otherwise.*

- **Rows** `[Shipping]` — thumb + name + meta + trailing; divider hairline. *(A native-semantics focusable base is `[Target]`, OD-17.)*
- **Sheets** `[Shipping]` — one chassis (`GothicSheet`) over one engine, **vaul** ([`docs/bottom-sheet-spec.md`](docs/bottom-sheet-spec.md), 2026-08-16). vaul owns motion and gestures only (1:1 drag, interruptible motion, velocity dismissal, rubber band, scroll-to-drag handoff); a hand-rolled spring engine was built first and abandoned after three device rounds — the swap kept the public API, so all 37 call sites were untouched. The chassis owns what a library cannot know, and every item is device-earned rather than decoration: the **`.cx-app` portal target** (the sheet's `position:fixed` must escape the pillar's transformed slide-pane); the **opaque self-compositing scroll body** (`translateZ(0)` + its own ground — on Android WebView a transform-animated ancestor with `overflow:hidden` fails to paint under a nested scroller and the sheet's lower half stays transparent until scrolled; **the rule most likely to break a library swap**, so it is applied explicitly, never assumed); **hardware back** through the LIFO consumer stack, still *consumed* when locked so nothing navigates underneath; the **`--kb` keyboard mechanism** with vaul's `repositionInputs` OFF so the two do not fight over the same sheet; **no background scaling** (it would transform the app root the sheet portals out of); and **an accessible handle** — a real `<button aria-label="Close">` rather than vaul's unnamed `<Drawer.Handle>`, because on the card sheets it is the only in-sheet exit (no X, by owner ruling) and vaul drags from the whole sheet anyway. Chrome is tokenized: `--surface-sheet` (#100c08 flat, owner-ruled), `--radius-sheet` 30px, `--shadow-sheet`, `--gold-handle`. `Sheet` is the one titled adapter (`BottomSheet` is an alias; titles are pinned headers everywhere). **RN sheet libraries (gorhom, true-sheet) are not options here** — they require React Native; their advertised "web support" means react-native-web, i.e. rewriting the render layer.
  - **ONE layer system, not two `[Shipping]`.** The chassis runs **stock vaul**, and anything that must paint *over* a sheet is built on **Radix Dialog** — the primitive vaul itself is built on — so both share one layer stack. Radix's modal mode puts `pointer-events:none` and a scroll lock on `<body>` and exempts only surfaces inside that stack, so a hand-rolled overlay opened above a sheet is dead and unscrollable while the sheet beneath still takes taps (the Settings bug, and every confirm raised from a sheet). **Any new over-sheet surface must be a Radix Dialog** — do not hand-roll a fixed overlay, and do not force past the manager with `pointer-events:auto`. One documented exception: `CardArtViewer`, a bespoke stage with its own phase machine, FLIP entrance, pointer-captured tilt and its own focus/inert/Escape handling, which opts back in at its root with a comment saying so.
- **Section rubric** `[Shipping]` — Cinzel gold caps + `.22em` tracking + a fade hairline (`SectionLabel`).
- **Pinned element** `[Shipping]` - a system-owned, always-present element that is not one of the user's own. It renders as a **gilt card** (a `linear-gradient(180deg, rgba(203,167,95,.07), rgba(203,167,95,.02))` field, a bright gilt `rgba(227,197,137,.42)` hairline at radius 19, a 54px glyph-in-a-circle, a 21px display title and a gold numeral) sitting under a `SectionLabel` rubric reading **PINNED**, above the user's own peers in their own labelled, counted sections. Two instances ship: the **Wishlist** on Collection > Lists and **Unfiled** on Collection > Storage. Two rules travel with the pattern: a pinned element never carries the row affordances its peers do (no drag handle, no rename, no delete, no overflow), and the peer section's count **excludes** it, because the count answers "how many have you made". Its detail screen names the class in the eyebrow and the instance in the title (PINNED / Unfiled), never the same word twice.
- **Empty / zero-image** `[Shipping]` — `BlankState` (rotated gold diamond + Cinzel title) and `CardArt`'s deterministic fallback; every surface must be legible with all art absent.
- **Waiting** `[Shipping]` — **exactly one loading indicator exists, and only a pillar earns it.** **`PillarLoading`** shows the brand diamond breathing (geometry in `brandMark.js`, breath in `tokens.css`), viewport-centred, on the **pillar chunk boundary only** — a genuine once-per-session wait, since `React.lazy` caches the chunk. **Every other wait renders nothing at all**: no mark, no ellipsis, no spinner. `Loading` is a **null render**, kept as a component at its ~25 call sites so `{x == null ? <Loading /> : …}` still states the intent and one edit could reinstate an indicator. Both prior treatments were rejected on device by the owner: the old ellipsis read as an unfinished frame, and putting the mark on every wait read as "a flash of a square" — those waits are a few frames of data and too brief to interrupt someone for. Two measured details worth keeping: the mark paints **instantly** (an earlier 140ms anti-strobe delay was wrong — frame forensics showed a cold pillar on an EMPTY body at 135ms, filling near 690ms, so the delay merely relocated the blank frame), and its breath starts at full strength and dips so the first frame never reads as a fade-in. It is **viewport-centred** (`position: fixed`) because a pillar wait has two phases in different boxes — the chunk load, then the pillar's own loading state after its header mounts — and centring in each moved the mark 105px between them.
- **Add-as-place** `[Target]` — adding is a property of *where you are*, not a hidden mode. This is the **Collection-redesign target interaction model, NOT current behaviour** (Collection ships an edit-mode toggle today).
- **Back** `[Shipping]` — the two-tier LIFO contract: ephemeral consumers (`back.js`) first, then the tested declarative precedence (`navBack.js`); never exits a live match on first press.
- **Header overflow** `[Shipping]` — `OverflowMenu`: a 44px dots trigger in a header (one circle at the §5 touch floor - an inner 34px styling span cost the button its accessible name in the WebView, so the button IS the circle), opening a small anchored menu of **manage-only commands** (never adding or importing). It shares the FAB-menu chassis and a common `MenuGlyph` set so glyph sizing is consistent.
  - **Boundary against the FAB, stated as a rule.** Adding lives on the `+` **FAB menu**; managing lives on the overflow. As shipped today: the **set drill** has **no overflow** - selection is its only manage action, so it is a direct **Select** pill in the header. It enters bulk-selection mode empty and then morphs in place into **Select all / Deselect all**; the docked search becomes the action bar, which just shows the running selected count (a single card is one tap on its tile). A one-item overflow is never used - promote it to a direct control. The **list-detail overflow** carries **rename, duplicate, export, delete** (the virtual Wishlist keeps only export); **Overview currently has no manage overflow**. On the FAB side, the **Collection and set `+` menus** offer **camera and typed import**; the **list `+` menu** is add-only - **add cards and add from text** (export is a manage action, so it sits in the overflow; the missing-card workflow lives on the progress bar's "View missing"; add-from-camera is deferred until the scanner learns a list target). A second FAB carries filter/sort where a surface needs it, so a screen may hold a refine FAB, a `+` FAB and an overflow — deliberately separate components rather than one with two anchors. (History: typed import once lived in the overflow; it moved onto the `+` FAB so the camera is never buried.)
  - **The rule that makes it learnable.** Adding is always the `+` FAB; managing is always the overflow.
  - **Promotion test.** If a command is used most visits it does not belong here — give it real chrome. The overflow is for the tail, not for hiding things that matter.
  - **It renders nothing when empty** — an affordance that opens an empty menu is worse than no affordance.
  - **HARD RULE — no `transform: scale()` on the panel.** It animates with opacity + a small translate only. The WebView accessibility tree keeps reporting a scale-morphing panel's pre-transition box: a 170px menu reports itself at ~36px. Fingers are unaffected (hit-testing uses the real box) but assistive tech gets the wrong target and `check:smoke` cannot drive it. Any future anchored menu inherits this rule. See [`BUILD.md`](./BUILD.md). *(The `Fab` menu — historically the violation this rule was written around — conforms as of the nav/search cohesion pass: opacity + 8px translate, static radius, and it carries `OverflowMenu`'s keyboard/focus model, so the app's two menus share one contract.)*

- **Collector seals — the corner-disc marks on a card tile** `[Shipping]` (owner ruling 2026-08-20). Two marks, one family, both in `CollectionCardViews.jsx`: a **24-viewBox minimal geometry**, filled with a **wash of its own hue at .16 alpha**, stroked at **1.6 with round joins**, and drawn on a **26px round dark disc** when it sits over card art.
  - **`PlaysetSeal`** — a **jade square-diamond + tick** = *this playset is complete*. Jade because completion is the app's success hue (`--jade-rgb`), and a SQUARE tick so it can never be read as the ROUND tick that means "card added".
  - **`FiledSeal`** — a **gold archive box** (a banker's box: wide lid overhanging the body, label slot on the front — owner redirect 2026-08-20 after a first cut read as a briefcase) = *this collector item (card + set) has copies in a named place*, either finish, any amount. Gold (`--gold-leaf`) because filing is a collection fact rather than a completion one, and geometric rather than pictorial so it reads as the diamond's sibling. It never means Unfiled: copies that are nowhere are not filed.
  - **Tile grammar (`BinderTile`)** — the playset disc takes the **first** top-right slot (`top: 6`), the filed disc the **second** (`top: 36`), and the filed disc **stays in the second slot whether or not the first is occupied**: a badge that hopped upward the moment a playset completed would make an unrelated event look like this one moved. Both hide in select mode, where that corner becomes the checkbox.
  - **Sheet grammar (`CollectionCardSheet`)** — the same two seals, at 16px, as one quiet inline row under the printing's product line, **playset first, filed second, no wordmarks** (each seal carries its own `title`/`aria-label`; a label beside a mark that already says it is noise). Both are read at **card+set grain and do not follow the finish toggle** — a playset is the two finishes together, and filed is true if either finish is in a place.
- **Ghost / empty slot** `[Shipping]` (pattern) — composed from `--surface-well` + inset shadow + dashed hairline; **not** a Foundation primitive. Empty-slot idioms already ship (AvatarPicker, counter sockets).

## 5 · Interaction

- **Motion** — tiers `[Target]` (`--dur/--ease`, §1.6); reduced-motion law is **`[Shipping]` and strong**: `body.reduce-motion` (class + `@media prefers-reduced-motion`) neutralises animation, with per-pillar *still-fallbacks* and a JS branch. Any new infinite/dramatic animation MUST ship a still fallback.
  - **Surface transition `[Shipping]` — ONE motion for every page/section swap (2026-08-21).** `.cx-surface-enter` / `@keyframes cxSurfaceEnter` in `tokens.css`: **opacity 0→1 with `translateY(6px)`→none, 200ms, `cubic-bezier(.2,.9,.3,1)`** (the house decelerate) — transform and opacity only, so the compositor carries it. **Mechanism:** the class goes on a plain content wrapper that is **keyed on the surface identity**, so React remounts it and the animation replays on every switch — no animation library, no timers, no exit state. **Where it applies:** a pillar's view chips (Collection Overview / My Collection / Lists), a segmented control that swaps the body (Collection All / Sets / Storage, Codex List / Card, the deck editor's List / Card), the Codex scope bar (Rules / Cards / Marginalia), and the in-place drills that replace the body under a header that stays put (a set, a list, a storage place, a Codex entry, Play's opponent record). It replaced a per-pillar inline `cxfade .2s ease`, which is why those swaps did not read as one app; **`cxfade` is now overlays and in-place image crossfades only** (dialog scrim, `.cx-picker-modal`, `.vc-modal-overlay`, boot splash, CodexDetail's printing swap) and must not be used for a surface again. **Rules it encodes** — the control that triggered the swap sits *outside* the wrapper so it does not ride the motion; **never on a scroll container** (transform + `overflow` on one element is the WebView blanking bug, §6); **no `animation-fill-mode`**, so no transform is retained — but the transform *is* live for those 200ms, so every `position:fixed` descendant must portal out (`Fab`/`SearchPill`/Collection's SelectionBar to the dock slots, sheets and **`AlphabetRail`** to `.cx-app` — the rail was moved onto a portal by this change for exactly this reason). **Reduced motion** deletes it outright (`@media prefers-reduced-motion` + `body.reduce-motion`), landing on the end state in one frame. **Deliberately not applied** to swipe-paged surfaces — Home Overview⇄Dashboard (`.cx-swipe-pane`) and Decks Library⇄My Deck⇄Stats — where a mount animation fights a 1:1 drag, nor to tab pages *inside* a sheet, where the sheet chassis owns motion. **Open owner question:** `.cx-swipe-pane` and `.cx-pillar-slide` are fade-only because their transform was removed as collateral of a since-disproven seam hypothesis (tokens.css comment, 2026-08-14); if the rise is wanted there too, that is an owner ruling, not an agent one.
  - **Rendering-integrity exception `[Shipping]`** (Codex-approved 2026-08-15, sole exception): the **ArtImg opacity reveal** (`cx-art-reveal`/`-warm`, 160/90ms, non-spatial) keeps its duration under reduced motion. It is not decorative — removing it re-exposes the image layer's measured first-raster tile-boundary flash (`docs/proposals/decks-swap-artifacts.md`). Implemented as higher-specificity `!important` in `tokens.css`; any future exception needs its own measured case and an owner ruling.
- **Haptics** — `[Shipping]`, graded semantics (`light`/`medium`/`heavy` by meaning) via `native.js:haptic()`. **Invariant `[Target]` (OD-20):** haptics must be **centrally gated** at one choke point — today the Settings toggle is **inert** (`haptic()` reads no setting; ~45 ungated callers). Implementation mechanism/wiring deferred to the adoption proposal.
- **State layer** — bespoke per-component `:active` (scale for cards, tint for controls) is **`[Shipping]`/Observed**; a real M3 ripple/state-layer is **`[Target]`/debt** (OD-16). `COMPENDIUM_ARCHITECTURE.md:201` already names ripple the code doesn't ship.
- **Selection** — **OWNER RULING 2026-08-20: selection controls are CIRCLES, app-wide.** A selectable thing carries the `BinderTile` check disc and nothing else: **24px, `border-radius: 50%`, a 1.5px hairline**, and when checked a **`--gold-leaf` fill with a dark `#1a1206` tick** (`stroke-width` 3, round caps). **Never a rounded square** — a squircle checkbox is another app's idiom, and the app had drifted into shipping both (Storage's place rows wore the last 7-radius square until this ruling). The round check disc is also what keeps the SQUARE playset seal (§4 Collector seals) unambiguous. Selection ENTRY stays the header **Select** pill, and the docked search bar becomes the action bar (§4 Header overflow).
- **Manual ordering** — **OWNER RULING 2026-08-20: manual list order is LONG-PRESS + DRAG, app-wide.** This is the only sanctioned gesture for arranging a list a person owns the order of; menu items that nudge one row a step at a time ("Move earlier / Move later") are **condemned** — a menu is where you manage a thing, not where you arrange a list. **The engine is `dnd-kit` (owner ruling 2026-08-21)**, adopted exactly as the sheet chassis adopted vaul (§4 Sheets): a hand-rolled gesture was built first and abandoned after three device rounds — scroll suppression, then a drop *bounce*, then a drop *flash* — and the swap kept our boundary while the library took the mechanism. **One module owns it app-wide:** `components/DragReorderList.jsx` (`DragReorderList` + `DragReorderRow`) over the pure `store/reorderModel.js`. Every new ordering surface adopts that pair; no pillar imports dnd-kit and no pillar re-derives a gesture. **The interaction values are unchanged and are the contract:** a **~400ms hold lifts** the row (a `medium` haptic, `scale(1.02)`, an elevated shadow, raised z); movement past **~8px before the timer fires cancels** the gesture, because a row is also a scroll surface and a flick must never become a reorder; a `light` haptic ticks on each slot change; displaced siblings slide and the drop settles under the library's own animation; the finger near an edge autoscrolls; and a row that navigates on tap has that click **suppressed** after a lift. Pinned rows are excluded **structurally** — rendered outside the draggable list, never clamped inside it. **What the library owns:** geometry, sensors and their activation constraints, autoscroll, and the drop/settle **handover frame**. *That frame is now a historical note.* It was the hardest part of the hand-rolled engine and the reason for the swap: the commit fired from `transitionend`, a **non-discrete** event, so React could defer the reorder render past the next paint while our own freeze had already stripped every transform — one frame of the old order, painted transform-free (reported on device, build 299, as a bounce and then a flash). All of that freeze/reflow machinery is deleted; the library's measured FLIP owns it. **What we still own:** the commit must apply the new order **synchronously** (the FLIP measures pre-render rects); and the **zoom boundary** — `.cx-app { zoom: var(--ui-scale) }` is a supported accessibility state, so every transform the library computes arrives in **viewport px** and is divided by the measured zoom **exactly once, at the CSS boundary** in `DragReorderRow`. Not in a modifier: modifiers only touch the *active* row, while the sibling displacement and the handover transform bypass them entirely. **Touch uses dnd-kit's `TouchSensor`, never `PointerSensor`** — the stock pointer recipe requires a permanent `touch-action: none` on the draggable and these rows *are* the scroll surface; `TouchSensor`'s non-passive `touchmove` is the only thing that stops an Android WebView scrolling under a lifted row. **An ordering clamp the query imposes is made VISIBLE instead — OWNER RULING 2026-08-21.** Decks are sorted `starred DESC, lib_order ASC`, so a favourite always outranks a plain deck; that boundary first shipped as an invisible clamp inside one flat list and read as decks refusing to go where they were dropped for no stated reason. The Library now carries the **section rubric** (§4, `SectionLabel`): **FAVOURITES** and **MY DECKS**, each with its row count, each **rendered only when it has rows** — no header over an empty section in either direction, and the same rule applies to what a search actually displays. **Each section is its own `DragReorderList`**, so a drag physically cannot leave the section it began in (`pillars/librarySections.js` maps a section-local drop back to the global order), and the header sits *between* the runs rather than inside one, where it would be measured as part of it. Shipping in **My Collection › Storage** ("Your Places", Unfiled pinned first and rendered outside the list) and **Decks › Library**. **Accessibility gap, stated not papered over:** the gesture is touch/pointer only. No `KeyboardSensor` ships, and dnd-kit's draggable ARIA attributes are deliberately *not* spread onto the rows — they would advertise a keyboard drag that does not exist on top of an already-clickable row. The menu items this replaced were tap- and screen-reader-reachable; drag reordering is not. Recorded as adoption debt beside OD-17.
- **Focus** — `:focus-visible` + `--focus-ring` is `[Target]` (OD-18); accessible focusable rows are `[Target]` (OD-17).
- **Typography weight** — Cinzel is requested at weight 800 but ships ≤700 (faux-bold on the 64–80px hero numerals). **Owner ruling OD-19: clamp usage to 700** (no 800 asset) — an adoption-track code change, `[Target]`/debt.

## 6 · Platform behaviour (hard law)

These are **`[Shipping]` constraints** — codify, do not change.
- **Zero-image degradation** — a **manual documented gate** (`cardArt.js:24` `imagesDisabled()` via `localStorage['cx-no-images']`; `CLAUDE.md:55` UI-work exercise). *There is no automated CI/test driving it.* **Rule:** every primitive must be fully legible and correctly laid out with all images absent; functional info lives in text/vector, never the photo; art slots reserve their box (`aspect-ratio`) and paint a deterministic fallback behind a self-removing `<img>`.
- **WebView paint** — never put a transform-animation and an overflow scroller on the same element (the `GothicSheet` fix); nested scrollers get their own opaque `translateZ(0)` layer. `mix-blend-mode` ships in **two** places: the film-grain (toggleable, non-load-bearing) and the full-art viewer's foil — two viewer-local layers under `isolation: isolate` (a `color-dodge` rainbow + an `overlay` glare, foil printings only, non-load-bearing, **verified in the installed Pixel Chromium WebView**, build 162). Treat blend-modes as engine-sensitive, **unverified until seen in the installed Chromium WebView** (`BUILD.md:178`). `backdrop-filter` is **not banned generally** (13+ sites ship it); the narrow rule (`counter.css:816`) is: **no `backdrop-filter` on a full-viewport overlay above a continuously-animating region** (per-frame full-screen re-raster). **OWNER RULING 2026-08-15: the frosted-glass look IS the aesthetic — performance is not a veto on modern devices; never strip blur as a perf lever without owner sign-off.** And a hard-won build rule: **declare ONLY the standard `backdrop-filter`, never a hand-written `-webkit-` pair** — the CSS minifier collapses the pair to the `-webkit-` alias alone, which Chromium 150+ (the System WebView) no longer parses, silently killing every .css-file blur while inline styles kept theirs (diagnosed via on-device CDP, build 238).
- **Offline-first, one sanctioned fetch** — every font, icon, texture, and **set-hero logo** is bundled and referenced by a relative/`BASE` URL. The **one** exception is **card art**, which streams from the Cloudflare R2 CDN through the art boundary (`useArtSource`/`ArtImage` → `artCache`) and caches on-device on first view; a miss falls to the deterministic element-gradient placeholder, so it is zero-image safe and a fresh-install-offline shows placeholders (art-CDN Phase 5). No *other* primitive may fetch a network resource, and no primitive builds an art URL by hand - it goes through the boundary (the `check:source` guard enforces both). Generate textures in CSS/SVG or bundle them.
- **Native vs web (Capacitor)** — use `env(safe-area-inset-*)` for edges and the CSS `--kb` keyboard token (**divided by `--ui-scale`**) for keyboard lift — never a native plugin or hand-rolled offset. Every native capability (haptics, share, status bar, blur) is progressive enhancement with a web fallback.
- **Accessibility floor** — ≥44px hit target today; **≥48dp is the `[Target]` floor** (OD-15) — `COMPENDIUM_ARCHITECTURE.md:201,203` mandate 48dp twice; current 44px recipe + the 34/30px offenders (RefineSheet operator/flip, OwnedControl stepper) are recorded as **adoption debt** (the RefineSheet numeric cluster wants a re-layout, not slop-padding). The nav/search cohesion pass brought the CHROME to the 44px floor via `tokens.css`'s `.cx-hit44` (invisible 44px hit expander) + `.cx-press` (the Manuscript press state — brightness lift, owner-ruled: no JS ripple): header backs/Done/bookmark, brand wordmark + profile chip, modal/sheet closes, SearchPill clear + help, Chip (expander), SegTabs (`minHeight: 44` — its container clips pseudo-expanders). `--ui-scale` zoom; `body.hc` high-contrast (reaches only `--ink-*`/`--hair-*` — hence the warm-muted-ink gap, OD-3); reduced-motion still-fallbacks; dialogs `role=dialog` + focus-trap + back-registered.

### Destructive confirmation — `[Shipping]` (whole-app replace)

The pattern for an action that destroys user data. Used by Restore backup; any future destructive
action should follow it rather than invent its own.

- **A confirmation is a CENTERED DIALOG, never a second bottom sheet.** Confirms are raised *from* sheets (delete profile from the profile sheet, delete match from the match sheet), and a second surface rising from the same edge with the same chrome reads as "the sheet changed" rather than "stop, this is irreversible". A centered dialog breaks the plane, and it cannot be flicked away — a destructive answer must cost a deliberate button press, never a careless downward swipe. Two stacked sheets also double-dim the screen and make drag-to-dismiss ambiguous. This matches both platforms: M3 puts destructive confirmation in a basic dialog, Apple in an alert; neither stacks a sheet on a sheet to ask a question. Implemented once in `ConfirmHost` (`CenteredModal`, z-700), so every `confirmAction()` caller inherits it and no future confirm can reintroduce the stack. *(A sheet over a sheet is still right when the second surface continues the same task rather than interrupting it — e.g. "Which printing?" over the collection card sheet.)*
- **The button names the consequence, not the intention.** "Replace all data", not "Restore".
- **`BTN_DANGER`, never `BTN_GOLD`.** Gold is the affirmative everywhere in this app; an
  irreversible replacement must not wear the same clothes as "Add".
- **Show both sides.** What the file contains AND what is on the device now that will be removed,
  with counts. A consequence the user cannot see is not a consequence they consented to.
- **No typed confirmation phrase.** Clear copy, a destructive-styled button and a verified,
  reachable safety copy are the protection. A phrase to copy out mostly trains people to copy
  phrases.
- **A reachable way back.** The safety copy is surfaced afterwards, persists across restarts, and
  returning to it uses this same pattern - undoing a replacement is itself a replacement.

**Accessibility contract:**

- **Initial focus lands on the consequence text, not the destructive button.** A screen reader must
  read what will be removed before reaching the control that removes it.
- The recovery affordance is a **labelled region**, because after a replacement it is the most
  important control on the screen and has to be findable.
- **Back cancels without writing**, and is suppressed while the operation is in flight.
- The button carries `aria-busy` during the operation.

### Foil — `[Shipping]` in the full-art viewer only
**Built and device-verified in `CardArtViewer.jsx`** (Pixel 9 Pro XL, build 162): a finger-tracked holographic sheen for foil printings — a `color-dodge` rainbow that ignites on the artwork's highlights plus an `overlay` glare, both under `isolation: isolate`, driven by one `requestAnimationFrame` spring loop. It meets every outcome constraint: **offline** (CSS gradients, no network/third-party textures), **reduced-motion safe** (a static sheen, no motion), **zero-image safe** (gated on **decoded** art identity `{src, gen}`, so it never renders over the element-gradient fallback), and **non-load-bearing** (removing it leaves a legible card). Finish comes from the active Collection printing; deck viewing is non-foil.

This is a **viewer-local implementation, NOT a universal foil primitive**. Any reuse on other surfaces (grids, thumbnails) is a **separate device-verified proposal** — the constraints above remain law; the specific CSS technique here is not automatically promoted app-wide.

### Arrange — grouping and stacked sorting — `[Shipping]` in List Arrange and Deck Add Cards
**`SortRow` (ui.jsx) · `sortStack.js` (reducer) · `sortOptions.js` (vocabulary) · `stackComparator` (collectionFilter.js)**

**Grouping is not sorting, and the two controls stay separate.** Grouping *sections* a view under headers; sorting *orders* it. Grouping is therefore **one level, single-select** — a binder's page divider. Nesting it was considered and rejected: 4 sets × 4 elements × 5 rarities is up to 80 headers on a 100-card list, most labelling one or two cards, and three tiers of pinned headers eat a phone viewport.

**Sort is an ordered stack.** Tap a key to add it, tap again to remove, and **tap order is priority order**, shown as a numbered gilt seal on the row. Each key carries its own direction, flipped by an arrow button on the row — which is why a vocabulary never ships both "Name A-Z" and "Name Z-A" as separate entries. "Group by Set · Element → Rarity → Name" is the canonical example: it reads like a binder.

**Options are metadata, not `[key, label]` tuples.** Each declares `{ key, label, defaultDir }`. `asc` means one thing everywhere — the natural forward order of the underlying value: A to Z, palette order, increasing scarcity, **oldest to newest**. A key whose label promises recency therefore ships `defaultDir: 'desc'` rather than redefining ascending. The reducer takes the **option object**, never a key it would have to look up, so there is no lookup to fail and no silent fallback to ascending; an option that does not declare a real direction is rejected rather than defaulted. This is not hypothetical tidiness — the reducer previously hardcoded ascending, which would have made "Recently added" list the oldest first.

**Ordering is total, in three steps:** the selected keys in priority order, then **implicit Name ascending**, then the row's own stable identity. Step two is required, not decorative: without it "sort by Rarity" would order each rarity run by opaque identity instead of alphabetically. Step three exists because names collide legitimately — a Wishlist is collector-item grain, so one card appears at several printings under one name.

**Absent values sort last in both directions.** Tails are ordered *before* direction is applied, so flipping a key never floats blanks to the top. For rarity there are two distinct tails, in this order: unknown/missing, then **avatars dead last** (they carry a real rarity but are not collected as rarity playsets). Descending reverses only the known values.

**Accessibility:** the priority number is announced, not just drawn (`aria-label` carries "sort priority 2 of 3, ascending"), and the row is keyboard-operable with `aria-pressed`.

**Scope today:** List Arrange and Deck Add Cards. **Collection refine deliberately remains single-sort** — parity is a separately proposed follow-up, gated on progressive render, the A-Z rail and ALL-view performance. This is not yet an app-wide idiom, and the two shapes coexist on purpose. See `docs/proposals/arrange-stacked-sort.md`.

### A-Z alphabet rail — `[Shipping]` in Collection (repo-green; interactive behaviour device-gated)
**`AlphabetRail.jsx`** — a vertical index on the logical inline edge of both Collection grids (ALL and the set drill). The rail itself is a **plain static track** of small Cinzel letters; the readout is a **big Cinzel letter pill that floats beside the thumb** while you scrub (offset inward so the finger never covers it). **Latch model:** a drag does ZERO grid work — no scroll, no re-render — it only moves the pill; the single jump fires on **release** (device tuning found live-scrubbing ~1,500 image tiles was the source of jank, and a floating-pill preview is the standard fix). **Structure & law:** a `<nav aria-label="Alphabetical index">` of letter `<button>`s (not a listbox) — **present** letters are focusable with `aria-current`; **absent** letters are inert, non-focusable, non-jumping slots. The hit model is a **continuous position-mapped strip**, so the letter comes from pointer Y (not a per-label button) — 27 labels stay reachable without each meeting the §5 touch floor. **Constraints met:** *offline* (text/vector only), *reduced-motion safe* (no decorative motion; jumps always work), *zero-image safe* (no art), *non-load-bearing* (thumb-scroll still reaches everything; the rail only shows when the order is globally alphabetical and **fails closed** — ducks — otherwise). **Geometry** clears the live dock/FAB obstruction via one measured boundary and is zoom-corrected for `--ui-scale` (`railGeometry.js`). All decisions live in tested pure helpers (`alphabetIndex.js`, `railGeometry.js`, `alphabetRailState.js`); the component is a thin shell with strict rAF/capture/listener teardown. **Interactive fidelity on the WebView is a device gate, not a repo claim.**

### Card-scanner reveal — "The Gilt Impression" — `[Shipping]` in the native scanner only (repo-green; motion device-gated)
**`scanner/ui/ScannerScreen.kt`** (Compose, native `ScannerActivity` — NOT the WebView) — recognition as ONE staged act on a **single shared clock** (`ScannerScreen` owns a `reveal` 0→1, shared by the stamp AND the result tray so they never drift apart). The scanner is a **pure snapshot** flow: an open viewfinder with no guide frame (portrait or landscape), a **gilt seal shutter**, and the captured photograph as the subject of everything that follows — the stamp lands on the user's own still. Luxe reads from **material depth**, not motion quantity: the stamp is a **gold double rule** (2.25dp outer, 1dp inner at 6dp inset) laid around the frozen photograph, preceded by a brief wide low-alpha **halo** flare that swells and quiets. The captured photograph stays visible throughout; **nothing is ever drawn over the artwork and no remote image is involved**.
**Three states (the loop is load-bearing — a scan must be *deliberate*, must *show its working*, and must *culminate*).** Haptics: one light tick on the shutter press, one `culminate()` when an identity settles. *Superseded and NOT rendered:* the live-OCR guide frame, its breathing violet “recognising” state and that state's repeated engagement tick, the “Hold steady” / “Position a card within the frame” copy, `CameraOverlay.kt`, and the ink-shadow / sheen / corner-boss layers of the old guide-rect stamp.
- **ready** — full-bleed preview, one parchment status line (*Fill the frame with one card, portrait or landscape, then tap*), and the shutter: a 72dp gold double-rule ring with a parchment centre dot. No idle animation.
- **reading** — the frame **freezes to the captured still**, which is exactly what the device is matching. The shutter’s ring hands over to a **violet arc** sweeping the same circle; reduced motion substitutes a static arc. Nothing is ever drawn over the artwork.
- **settled** — the gilt double-rule **stamps around the frozen photograph** (contact, then the inner rule, then a brief halo) and the existing result sheet rises carrying the card name. Brightness and stroke weight only — **never scaling** — settled by ~650ms. Coloured by the **result’s type accent token** (gold card / violet deck / jade match via `accentFor()`). When the match is uncertain the reveal is WITHHELD and a text-first shortlist is offered instead: the ceremony belongs to a settled identity, never to a guess.
**Result tray** rides the same clock — it **arrives late** (≈0.52→0.875 of the reveal) so it never competes with the frame + name beats, and its heading is **compact** (the large gilt name above the frame is the payoff; the tray restates it quietly, ≤2 lines) rather than a second big title.
**Recognition is FROZEN while a result is shown** (`ScannerViewModel` ignores further OCR/QR matches until "Scan another" / a completed action) so the recognised identity can never change under a user reaching for an action.
**Haptics (build → climax):** a light engaged tick on entering recognising, then a **growing pulse ramping to a firm finish** timed so its peak coincides with the gold flare (the 1.0.2 "achievement" feel) — not a single flat tick.
**Type:** the app's shipping families (`--f-display`/`--f-read`/`--f-ui`) bundled as TTFs in `res/font` — **Cinzel** for the card name + sheet rubric/title, **Hanken Grotesk** for status/labels/controls (scanner MaterialTheme + `LocalTextStyle` default to it, so nothing is system Roboto), **EB Garamond** for reading copy.
**Name divider:** the manuscript centre-weighted fade gilt hairline (transparent→gilt→transparent). **Gilded depth is stacked opacity on ONE hue**, **never a gradient along the stroke** (the "cheap foil" look). **Close control:** the app language — a **gold X in a round button, top-right (48dp)**; the reveal text is offset below that corner. **Ownership line ("In My Collection ×N") is DEFERRED to Phase 2** — a decorative count must not display before its write is acknowledged; the ceremony shows the name only.
**Reduced-motion (`[Shipping]`, strong):** the resolved app preference (`body.reduce-motion`, folded from the user setting OR OS `prefers-reduced-motion` by `appearance.js`) is passed at `scan()`; the shared clock snaps to 1 → the settled impression, name, and tray appear in one frame — no press/breath/halo/loop. **Constraints met:** *offline* (Canvas vector only; recognition never waits on or uses the remote image), *zero-image safe* (no card art drawn), *non-load-bearing* (recognition + the action tray work with the reveal removed), *performant* (~16 draws at peak; steady states run zero animation). **Deliberately excluded:** camera→card-render crossfade, any effect over the artwork, foil gleam, perimeter trace, expanding ripple, full-frame glow bloom, sparkle/particles, spring/overshoot, frame scaling, multi-part haptics, gradients along strokes. **Motion fidelity, TalkBack, incorrect-match recovery, short-screen layout, and per-frame performance on the installed Compose surface are device gates, not repo claims.**
